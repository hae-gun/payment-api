# 멱등성 처리

- IdempotencyKey 를 사용하여 요청을 구분하고, 동일한 요청이 들어왔을 때 이전 결과를 반환하도록 합니다.
- IdempotencyKey 는 null이 될 수 없으며, 최대 100자까지 허용됩니다.

## 승인 흐름에서의 멱등성 처리

1. 요청이 온다 (key, amount)

2. key 로 저장된 Payment 를 찾는다

3. 없으면
   Payment 를 만들어 저장한다 (PENDING)          ← 커밋
   PG 에 승인을 호출한다                          ← 트랜잭션 밖
   결과에 따라 approve() / fail() / markUnknown() ← 커밋
   결과를 돌려준다

4. 있으면
   금액이 다르면  → 거절한다
   금액이 같으면  → 저장된 것을 그대로 돌려준다
   PG 를 다시 부르지 않는다

5. 같은 순간에 두 요청이 도착하면 둘 다 2번에서 "없음"을 보고 3번으로 들어간다.
   저장 시점에 idempotency_key 유니크 제약 위반이 발생하는 쪽이 두 번째 요청이며,
   이를 잡아 4번의 "금액이 같은 경우"와 같이 처리한다.

### 금액이 다를 때 거절하는 이유
- 같은 키인데 금액이 다르면 그건 재시도가 아니다. 클라이언트가 키를 재사용했거나
  버그다. 여기서 첫 결과를 그대로 돌려주면 클라이언트는 자신이 보낸 금액으로
  결제가 성립했다고 믿게 되므로, 거절해서 불일치를 드러낸다.

### PENDING 재요청을 이어받지 않기로 한 이유
- 현재 상태로는 PENDING 의 상태가 PG 요청을 수행한 상태인지 아닌지 알수 없음
- PG 에 동일한 요청을 전송하는것을 방지하기 위해 재요청을 이어받지 않기로 함
- 만약 재요청을 진행하려면 PENDING 을 READY 와 IN_PROGRESS 상태로 분리하고 READY 일때만 PG 요청을 재요청하는 방향으로 수정 필요함 

### 트랜잭션을 셋으로 나눈 이유
- PG 호출은 롤백할 수 없다. 트랜잭션 안에서 호출하면 PG 승인이 성공한 뒤에
  우리 쪽 저장에서 예외가 나 롤백될 수 있고, 그러면 Payment 는 남지 않는데
  외부 PG 서버에는 승인이 남는다.
- PG 호출 전에 기록이 남아야 한다. 기록이 있어야 PG 를 호출하려 했다는 사실을
  나중에 확인할 수 있다. 다만 현재 모델은 PENDING 이 "아직 안 부름"과
  "부르고 대기 중"을 구분하지 못하므로, 안전한 쪽인 "이미 불렀다"로 간주한다.
- PG 호출은 수 초가 걸린다. 트랜잭션 안에서 호출하면 그동안 DB 커넥션을 붙잡고 있게 되고, 동시 요청이 몰리면 커넥션 풀이 고갈된다.

## 기능 요구사항

| # | 요구사항                                                                  | 테스트 |
|---|-----------------------------------------------------------------------|---|
| 1 | 신규 요청되면 PENDING 으로 저장 한 후 PG 를 호출한다.                                  |   |
| 2 | PG 승인이 성공하면 APPROVED 상태로 저장한다.                                        |   |
| 3 | PG 승인이 실패하면 FAILED 상태로 저장한다.                                          |   |
| 4 | PG 요청의 응답이 무응답 일때 UNKNOWN 상태로 저장한다.                                   |   |  
| 5 | 등록된 승인 요청키로 중복 수신시 이전 등록된 Payment 객체를 반환하며 PG 요청은 진행되지 않는다.           |   |
| 6 | 등록된 승인 요청키 이지만 금액이 다른경우 IdempotencyKeyConflictException 에러를 반환한다.         |   |
| 7 | 동일한 승인 요청키로 동시에 수신되면 1개의 요청만 승인 처리되며, 다른 하나는 앞서 처리된 Payment 객체를 반환한다. |  |
| 8 | PG 호출은 트랜잭션에 포함되지 않는다.                                                |  |
